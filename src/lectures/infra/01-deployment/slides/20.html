DOCKER / 09 · безопасность образа

Trivy проверяет образ до запуска

Команда · сохранённый пример
$ trivy image --scanners vuln \
    demo-backend:1
Сокращённый учебный отчёт
Пакеты ОС       HIGH: 1
Python-пакеты   CRITICAL: 1

В полном отчёте смотрим пакет, установленную и исправленную версии.

Команда · сохранённый пример
$ docker build -t demo-backend:2 .
Перед сборкой изменены файлы
Dockerfile → базовый образ
requirements.txt → пакеты
новый образ → demo-backend:2
Команда · сохранённый пример
$ trivy image --scanners vuln \
    --severity HIGH,CRITICAL \
    --exit-code 1 demo-backend:2
Сокращённый учебный отчёт
HIGH: 0   CRITICAL: 0
код возврата: 0

Проверка прошла по выбранному порогу.

Нашли уязвимость → обновили компоненты → пересобрали и проверили образ снова.

Сценарий: это сохранённый учебный пример, не результат реального запуска Trivy. Перед каждым кадром спросить, что должно измениться. Пробел — дальше, Shift + пробел — назад, R — сброс.

Сказать: Trivy сопоставляет найденные в образе пакеты ОС и Python с базами известных уязвимостей. --scanners vuln оставляет только поиск уязвимостей. В отчёте важны затронутый пакет, его версия, severity и наличие исправленной версии. После изменения FROM или requirements.txt нужно собрать новый образ и сканировать именно его. --severity оставляет выбранные уровни; --exit-code 1 позволяет сделать наличие таких находок причиной неуспеха проверки. Без этого флага находки сами по себе обычно не дают ненулевой код возврата.

Граница: счётчики и нулевой результат в кадрах вымышлены; готового backend и Trivy в стенде пока нет. Результат зависит от образа и версии базы уязвимостей; для первого обновления базы нужен доступ к источнику данных. Отсутствие находок не доказывает безопасность приложения, а severity не равна доказанной эксплуатируемости.

Спросить: достаточно ли исправить Dockerfile, чтобы Trivy проверил новый образ? Ответ: нет, образ надо пересобрать и повторно просканировать.

Источники: сканирование образов Trivy; параметры trivy image.
