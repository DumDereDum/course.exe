DOCKER / 04 · namespaces

Один процесс —
разные представления.

Из Ubuntu в demo · PID условный
backend: PID 4280
ps: процессы ВМ
/: файлы гостя
net: сеть ВМ
Из контейнера backend
backend: PID 1
ps: свои процессы
/: корень образа + запись
net: свои интерфейсы

PID, mount и network namespaces меняют взгляд на один процесс и его окружение.

Сказать: процесс backend принадлежит дочернему PID namespace контейнера и виден также из родительского пространства имён Ubuntu. Поэтому хост может видеть процесс под своим PID, а контейнер — под PID 1. Из контейнера нельзя увидеть процессы родительского PID namespace. Число 4280 условное, его нельзя выдавать за результат реального запуска.

Файлы: mount namespace отделяет набор монтирований. Docker готовит корень из слоёв образа и собственного слоя записи; bind mount может намеренно открыть каталог хоста внутри контейнера. Сеть: network namespace даёт отдельные интерфейсы и маршруты; при обычном bridge-подключении контейнер связывается с сетью ВМ через инфраструктуру Docker.

Граница схемы: показан запуск без дополнительного init-процесса. Если использовать docker run --init, PID 1 внутри контейнера получит init, а backend станет его потомком. PID namespace, mount namespace и network namespace решают разные задачи; они не создают нового ядра Linux.

Спросить: почему ps внутри контейнера и ps в Ubuntu показывают разные PID для backend? Ответ: они смотрят из разных PID namespaces.

Источники: PID namespaces; mount namespaces; сеть bridge.
