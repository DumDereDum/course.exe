Как воспроизводимо развернуть приложение?

Саратовцев Артём · ВШЭ НН
01

Начало: коротко назвать тему и вопрос занятия. Сегодня разбираем виртуальные машины, контейнеры, сети и автоматизацию настройки. Время: около 1 минуты.

Спросить: с какими из этих инструментов уже работали? Ответ: открытый; оценить практический опыт группы и перейти к устройству виртуальной машины.

Сценарий: после титула перейти к устройству виртуальной машины и ролям QEMU и KVM. Архитектуру полного стенда и задание лабораторной показать после разбора инструментов, в конце лекции. Реальный стенд пока не подготовлен.

KVM / 01 · роли

Гость видит свой компьютер.
QEMU и KVM делят работу.

Обычные инструкции → KVM; запуск ВМ → QEMU → KVM; диск и сеть → QEMU.

Сказать: QEMU — процесс Linux: он собирает модель машины, выделяет память и открывает файл диска. Через /dev/kvm QEMU создаёт ВМ и vCPU, а затем запускает выполнение. KVM — модуль ядра Linux. Он даёт обычным инструкциям гостя выполняться на физическом CPU с аппаратной виртуализацией.

Устройства: когда гостю нужны диск или сеть, он обращается к виртуальному устройству. В типичном простом пути выполнение выходит из KVM в QEMU; QEMU обслуживает устройство с помощью файловой или сетевой подсистемы Linux. Некоторые операции ускоряются в ядре и не возвращаются в QEMU.

Спросить: кто открывает файл виртуального диска, а кто выполняет обычные инструкции гостя? Ответ: QEMU открывает файл; KVM обеспечивает выполнение инструкций на физическом CPU.

Граница схемы: стрелки показывают логические обязанности, а не каждый переход между режимами процессора. Гостевая ОС не вызывает QEMU как обычную библиотеку.

QEMU подготавливает машину; гостевая ОС проходит обычные этапы загрузки.

Сказать: QEMU читает конфигурацию, выделяет память и открывает файл диска. Через /dev/kvm он просит ядро создать ВМ и виртуальные процессоры, связывает гостевую память с памятью своего процесса. После запуска vCPU выполняется прошивка BIOS/UEFI, затем загрузчик и ядро гостевой ОС.

Спросить: что загружается раньше гостевой ОС? Ответ: виртуальная прошивка и загрузчик.

Граница схемы: порядок некоторых операций подготовки зависит от конфигурации QEMU; здесь показаны смысловые этапы, а не трасса системных вызовов.

Кто распределяет время

Linux планирует потоки QEMU вместе с остальными процессами хоста.

vCPU — не отдельный чип: его код исполняется на общем физическом CPU.

Сказать: гостевая ОС считает, что у неё есть собственный процессор. В обычной конфигурации QEMU каждому vCPU соответствует поток хоста. Поток вызывает KVM_RUN, и гостевые инструкции выполняются физическим CPU с аппаратной поддержкой виртуализации. Планировщик Linux решает, когда поток получает время.

Пример: если ВМ получила два vCPU, это не резервирует для неё два физических ядра: потоки конкурируют за время с другими задачами хоста.

Спросить: сможет ли Linux на хосте выполнять другие процессы, пока работает ВМ? Ответ: да; он планирует потоки ВМ вместе с остальными.

→

→

→

Обратный путь

Данные возвращаются гостю, и его выполнение продолжается.

Для гостя это диск; для хоста — файл или другое устройство хранения.

Сказать: гостевая ОС обращается к виртуальному диску через драйвер. В простом варианте KVM возвращает управление QEMU, QEMU обрабатывает запрос виртуального устройства и просит Linux прочитать данные из файла образа. Затем результат становится доступен гостю, при необходимости через виртуальное прерывание.

Спросить: где физически лежат данные виртуального диска? Ответ: в хранилище хоста, например в файле образа ВМ.

Граница схемы: это один типичный путь. Virtio и механизмы ускорения могут перенести часть работы в ядро; не каждый запрос обязательно полностью проходит через QEMU.

Установщик меняет диск ВМ, а не операционную систему Linux-хоста.

Сказать: QEMU подключает установочный ISO как виртуальный носитель и создаёт отдельный пустой виртуальный диск. ВМ загружается с ISO. Установщик внутри гостя размечает диск и записывает на него файлы ОС. В этом примере виртуальный диск хранится как файл на хосте. После установки ISO отключают и запускают ВМ уже с диска.

Спросить: куда установщик записывает ОС? Ответ: на виртуальный диск ВМ; в нашем примере это файл на Linux-хосте.

Граница примера: конкретный дистрибутив и формат диска здесь не заданы. Позже в практическом стенде используется cloud image — виртуальный диск с уже установленной ОС, поэтому шаг с ISO и установщиком пропускается.

Сказать: в PowerShell с правами администратора команда wsl --install включает нужные компоненты и устанавливает дистрибутив по умолчанию; может потребоваться перезагрузка. Спросить: где выполняются Linux-команды после открытия дистрибутива? Ответ: в Linux-среде WSL2, работающей внутри Windows.

Граница: показана типовая установка на поддерживаемой версии Windows; конкретные требования и возможные ошибки зависят от компьютера. На следующем слайде отдельно проверяется возможность запускать KVM внутри WSL2.

sudo apt update

  -m 512 -display none \
  -monitor stdio

Ubuntu x86-64 внутри WSL2. В мониторе QEMU: info kvm, затем quit. Диск не подключён.

Сказать: WSL2 уже работает в виртуальной машине. Если Windows передаёт ей аппаратные возможности виртуализации, модуль KVM внутри Linux-ядра WSL2 может выполнять код ещё одной гостевой ВМ. QEMU запускается как процесс внутри дистрибутива и обращается к /dev/kvm.

Показ: команды рассчитаны на Ubuntu x86-64 внутри WSL2. Установить QEMU, проверить наличие /dev/kvm, затем запустить пробную ВМ с явным ускорителем KVM. sudo использован только для этой короткой проверки, чтобы не зависеть от членства пользователя в группе kvm. Диск не подключён: гостевая ОС не загружается, но QEMU создаёт ВМ и запускает виртуальный CPU. В мониторе QEMU команда info kvm должна показать активный KVM; quit завершает процесс. Если ускоритель недоступен, QEMU выдаст ошибку вместо незаметного перехода на программную эмуляцию.

Граница проверки: наличие /dev/kvm само по себе недостаточно. Параметр nestedVirtualization в .wslconfig влияет на доступность вложенной виртуализации, но её работоспособность зависит также от Windows, CPU, ядра WSL и политик компьютера. Реальный запуск на WSL2 здесь не выполнялся.

Спросить: сколько уровней ВМ здесь показано? Ответ: два: среда WSL2 и гостевая ВМ, которую запускают QEMU и KVM внутри неё.

Переход: после проверки KVM можно подключить к ВМ установочный ISO или готовый образ диска. Конкретная среда для практического стенда ещё не проверена.

ANSIBLE / 01 · подготовка хоста

Ansible готовит
Linux-хост для ВМ.

create-vm.yml · KVM-хост
- name: Пакеты для KVM
  ansible.builtin.apt:
    name:
      - qemu-kvm
      - libvirt-daemon-system
      - virtinst
    state: present
    update_cache: true
На Linux-хосте · demo: 2 vCPU, 2 ГБ
Ansible
   ├─ apt → QEMU + libvirt
   └─ get_url → cloud image
                   │
                   ▼
                demo.img

В образе уже установлена Ubuntu.

Сказать: пример рассчитан на Ubuntu-хост с доступным KVM, который проверяли ранее. Для простоты Ansible запускается на этом же хосте: inventory содержит группу kvm_host и строку localhost ansible_connection=local. Команда запуска — ansible-playbook -i inventory.ini create-vm.yml. В play с hosts: kvm_host и become: true задача apt устанавливает пакеты на экране. Следующие задачи получают готовый cloud image Ubuntu и создают из него отдельный диск demo.img, сохраняя существующий диск при повторном запуске. Для модуля создания ВМ дополнительно нужны коллекция community.libvirt, привязки Python к libvirt и lxml. На экране показан фрагмент playbook, а не готовый стенд.

Спросить: где выполняется задача apt? Ответ: на Linux-хосте с KVM, ещё до запуска гостевой Ubuntu.

Источники: пакеты libvirt в Ubuntu; cloud image и libvirt.

ANSIBLE / 02 · запуск ВМ

Ansible задаёт параметры,
libvirt запускает ВМ.

create-vm.yml · создание demo
- community.libvirt.virt_install:
    name: demo
    memory: 2048
    vcpus: 2
    disks: [{path: "{{ vm_disk }}"}]
    import: true
    cloud_init:
      clouduser_ssh_key: "{{ key_file }}"
Кто что делает
Ansible
   │ virt_install
   ▼
libvirt
   │ запускает
   ▼
QEMU + KVM ──→ demo

vm_disk — диск ВМ; key_file — публичный SSH-ключ. Сеть — default.

Сказать: это следующая задача playbook create-vm.yml. Переменная vm_disk указывает на отдельный диск demo.img, созданный из готового cloud image. Параметр import означает загрузку уже установленной ОС, без установщика с ISO. В полной задаче дополнительно указана сеть networks: [{network: default}], которую нужно заранее активировать в libvirt. cloud_init передаёт путь к публичному ключу на хосте; cloud-init внутри Ubuntu добавит ключ для первого SSH-доступа. Задача Ansible обращается к libvirt через virt-install; libvirt запускает процесс QEMU, а тот использует KVM. По завершении playbook ВМ продолжает работать. Для этого модуля нужны virtinst, коллекция community.libvirt, привязки Python к libvirt и lxml.

Спросить: кто выполняет инструкции гостевой Ubuntu после завершения playbook? Ответ: ВМ продолжает выполняться через QEMU и KVM; Ansible лишь создал и запустил её.

Источники: модуль virt_install; запуск cloud image.

Новый адресат

   │ SSH
   ▼
Ubuntu в demo

inventory.ini: demo ansible_host=192.168.122.100 ansible_user=ubuntu. IP здесь — пример. Повторный запуск не ставит Nginx заново.

Сказать: после запуска ВМ узнаём её фактический IP-адрес в сети libvirt и записываем его в inventory; 192.168.122.100 на экране — только пример, DHCP может выдать другой адрес. Команда ansible-playbook -i inventory.ini configure-vm.yml запускает второй playbook. Ansible подключается к гостевой Ubuntu по SSH с ключом, переданным через cloud-init, и выполняет задачу apt уже внутри гостя. become: true даёт права для установки пакета. state: present описывает требуемое состояние: если Nginx уже установлен, повторный запуск не устанавливает его заново. Это подготовленный пример, реальный адрес и доступность SSH должны быть проверены на стенде.

Спросить: на каком компьютере установится Nginx? Ответ: в гостевой Ubuntu внутри ВМ demo, потому что play обращается к хосту demo из inventory.

Источник: plays и задачи Ansible.

DOCKER / 02 · образ и контейнер

Образ задаёт основу.
Контейнер получает состояние.

Образ backend:v1

Слои только для чтения: среда выполнения, библиотеки и код.

В настройках — рабочий каталог и команда запуска.

Два контейнера из образа
backend:v1
   ├──→ A: процесс + слой записи
   └──→ B: процесс + слой записи

Остановленный контейнер можно запустить снова.

docker build создаёт образ; docker run создаёт и запускает новый контейнер.

Сказать: образ — подготовленная основа: файлы и настройки запуска. Из одного образа можно создать несколько контейнеров. Их слои образа общие и доступны только для чтения, а изменения файлов каждый экземпляр пишет в свой слой. При запуске у каждого появляется свой главный процесс. Остановленный контейнер остаётся существовать до удаления.

Команды: docker build создаёт образ; docker run создаёт и запускает новый контейнер. backend:v1 на схеме — условное имя будущего образа, а не уже подготовленный стенд.

Спросить: если контейнер A создаст файл в своём слое, увидит ли его контейнер B? Ответ: нет, без общего тома или другого механизма обмена данными.

Сказать: docker CLI обращается к API демона dockerd. Демон готовит образ и конфигурацию контейнера и передаёт управление жизненным циклом containerd. Ядро гостевой Ubuntu предоставляет файловую систему, пространства имён, cgroups и выполнение инструкций. docker run совмещает создание контейнера и его запуск; когда главный процесс завершается, контейнер останавливается.

Граница схемы: стрелки показывают роли компонентов, а не точное дерево процессов или последовательность системных вызовов. backend:v1 — условное имя будущего образа, реальный стенд ещё не готов. В нашем стенде Docker-хост — гостевая Ubuntu в ВМ demo, а не физический KVM-хост.

Спросить: какое ядро выполняет backend? Ответ: ядро Ubuntu внутри ВМ demo.

Источники: Docker Engine; containerd и runc.

DOCKER / 04 · namespaces

Один процесс —
разные представления.

Из Ubuntu в demo · PID условный
backend: PID 4280
ps: процессы ВМ
/: файлы гостя
net: сеть ВМ
Из контейнера backend
backend: PID 1
ps: свои процессы
/: корень образа + запись
net: свои интерфейсы

PID, mount и network namespaces меняют взгляд на один процесс и его окружение.

Сказать: процесс backend принадлежит дочернему PID namespace контейнера и виден также из родительского пространства имён Ubuntu. Поэтому хост может видеть процесс под своим PID, а контейнер — под PID 1. Из контейнера нельзя увидеть процессы родительского PID namespace. Число 4280 условное, его нельзя выдавать за результат реального запуска.

Файлы: mount namespace отделяет набор монтирований. Docker готовит корень из слоёв образа и собственного слоя записи; bind mount может намеренно открыть каталог хоста внутри контейнера. Сеть: network namespace даёт отдельные интерфейсы и маршруты; при обычном bridge-подключении контейнер связывается с сетью ВМ через инфраструктуру Docker.

Граница схемы: показан запуск без дополнительного init-процесса. Если использовать docker run --init, PID 1 внутри контейнера получит init, а backend станет его потомком. PID namespace, mount namespace и network namespace решают разные задачи; они не создают нового ядра Linux.

Спросить: почему ps внутри контейнера и ps в Ubuntu показывают разные PID для backend? Ответ: они смотрят из разных PID namespaces.

Источники: PID namespaces; mount namespaces; сеть bridge.

DOCKER / 05 · ограничения ядра

Ядро ограничивает ресурсы и действия.

Один процесс · три механизма
backend
  ├─ cgroups       → CPU, память, процессы
  ├─ capabilities  → привилегированные действия
  └─ seccomp       → системные вызовы
Пример лимитов

--memory=256m · --cpus=1 · --pids-limit=64 — значения задают явно.

Ограничения применяет ядро Ubuntu в ВМ demo, общее для контейнеров.

Связь: namespaces на предыдущем слайде меняют видимые ресурсы. Здесь показать другие механизмы: сколько ресурсов процессу доступно и какие действия он может выполнять.

Сказать: cgroups учитывают процессы и могут ограничить память, долю CPU и число процессов. Конкретные значения лимитов появляются после явной настройки; один только факт принадлежности контейнера cgroup не означает ограничение памяти в 256 МБ. Capabilities делят полномочия root на отдельные права, и Docker по умолчанию оставляет ограниченный набор. Seccomp фильтрует системные вызовы, через которые процесс обращается к ядру. Это параллельные механизмы, не три последовательных шага.

Граница модели: контейнеры используют общее ядро Ubuntu в ВМ demo. Права, монтирования и режимы запуска меняют степень изоляции; например, --privileged существенно расширяет возможности контейнера. Значение --cpus=1 задаёт квоту CPU, а не закрепляет за контейнером отдельный физический процессор.

Спросить: какой механизм ограничит память, а какой проверит допустимость системного вызова? Ответ: cgroups и seccomp соответственно.

Источники: cgroup v2; безопасность Docker Engine; seccomp в Docker.

DOCKER / 12 · Compose

Compose описывает запуск нескольких сервисов

compose.yaml
services:
  web:
    image: demo-web:1
    ports: ["80:80"]
  backend:
    image: demo-backend:1
После docker compose up -d
ВМ demo:80 → web:80
web → backend:8000
сеть: <проект>_default

Оба сервиса входят в общую сеть; имя backend доступно из web.

Compose создаёт контейнеры и сеть из файла; наружу опубликован только web.

Сказать: Compose читает compose.yaml и создаёт сервисы как контейнеры одного проекта. Без явного networks он создаёт сеть default; сервисы находят друг друга по имени. ports публикует порт 80 web на порту 80 Ubuntu внутри ВМ demo. У backend нет ports: его порт 8000 доступен web в общей сети, если приложение слушает на этом порту.

Граница: Compose не настраивает прокси автоматически: образ web должен содержать конфигурацию обращения к http://backend:8000. Имена образов учебные; готовых web и backend в стенде пока нет. -d запускает сервисы в фоне.

Спросить: сможет ли клиент снаружи ВМ обратиться к backend:8000 напрямую? Ответ: нет, его порт не опубликован; клиент идёт через web при настроенном прокси и сетевом доступе к ВМ.

Источники: модель Compose; сеть Compose.

Сказать: сервисы Compose в одной сети находят друг друга по имени. Адрес backend:8000 используется внутри web при настроенном прокси; IP контейнера может меняться. up -d запускает сервисы в фоне. stop не удаляет контейнеры, их записываемые слои и сеть: их можно снова запустить через compose start. down удаляет контейнеры с их записываемыми слоями и сеть, но по умолчанию сохраняет образы и именованные тома. down -v удалит и тома проекта.

Граница: пример предполагает уже подготовленные образы demo-web:1 и demo-backend:1 из предыдущего слайда; реального стенда пока нет. Имя сети зависит от имени проекта.

Спросить: после down новый контейнер web получит прежний записываемый слой? Ответ: нет; постоянные данные следует хранить в томе или внешнем хранилище.
