# Мини-практика 1: SAST — 10 минут

Цель: пройти цикл «запуск → разбор → исправление → повторная проверка». Учебная программа выводит сообщение о задаче; режим retry дополнительно выводит сообщение о повторной обработке. В одном пути есть дефект управления ресурсом.

## До занятия

Нужен Clang Static Analyzer. Можно работать в подготовленном Ubuntu-контейнере или локально с установленным Clang. Сборку среды выполнить заранее, вне десятиминутной практики.

Установите Docker и запустите его службу (в Docker Desktop — откройте приложение). Скачайте архив практики и распакуйте его в отдельную папку. В этой папке находятся Dockerfile, task.c и check.sh.

Dockerfile использует Ubuntu 24.04, устанавливает Clang и задаёт рабочую папку /work. Из папки с Dockerfile на своём компьютере выполните:

```sh
docker build -t rbpo-sast .
docker run --rm -it \
  -v "$PWD:/work" rbpo-sast
```

`docker build` собирает образ rbpo-sast по Dockerfile из текущей папки. `docker run` открывает Bash в контейнере; `-v` подключает текущую папку компьютера к /work, `--rm` удаляет контейнер после выхода, сохраняя файлы в подключённой папке.

В открывшемся контейнере проверьте установку:

```sh
clang --version
```

Далее все команды анализа и `sh check.sh` выполняйте в этом контейнере. Редактируйте task.c на своём компьютере: контейнер видит изменения в подключённой папке. В контейнере не требуется устанавливать редактор. Архив содержит файлы непосредственно в своём корне. Для выхода выполните `exit`; для повторного входа повторите `docker run`. После изменения task.c пересобирать образ не требуется.

## Во время практики

8 минут самостоятельной работы и 2 минуты общего разбора.

1. **2 минуты:** напрямую запустите Clang командой ниже, затем прочитайте отчёт через `cat`. Откройте `reports/sast.txt`, выделите место, правило и условия пути.
2. **2 минуты:** подтвердите находку по исходникам, определите её CWE и запишите короткое обоснование TP. Отметьте две операции, которые приводят к дефекту.
3. **2 минуты:** исправьте причину в `task.c`. Ресурс должен освобождаться ровно один раз и при обычном завершении, и при retry. Сохраните оба сообщения программы. Подавление предупреждения не считается исправлением.
4. **2 минуты:** повторите ту же команду Clang, прочитайте новый отчёт, затем выполните `sh check.sh` на исправленном коде.

Критерий завершения: повторный анализ успешно завершился, прежней находки нет, оба режима проходят проверку. Сохраните изменённый task.c и reports/sast.txt; добавьте статус TP, CWE и причину исправления в короткую заметку.

## Прямой запуск анализатора

```sh
mkdir -p reports
clang --analyze task.c \
  -Xanalyzer -analyzer-output=text \
  2> reports/sast.txt
cat reports/sast.txt
```

После исправления повторите команду Clang с теми же параметрами и прочитайте перезаписанный отчёт. `mkdir -p reports` можно повторять: существующая папка сохраняется.

- `--analyze` включает статический анализ.
- `-Xanalyzer` передаёт следующий параметр анализатору.
- `-analyzer-output=text` выбирает текстовый формат.
- `2>` перенаправляет stderr в файл и перезаписывает старый отчёт.
- Обратный слеш в конце строки продолжает команду.

Проверьте код завершения командой `echo $?` сразу после Clang, до `cat`: ожидается 0. Предупреждения анализатора обычно не делают его код ненулевым, поэтому отчёт всё равно нужно прочитать. Ошибка компиляции или запуска не считается успешно выполненным анализом.

`check.sh` используется только для сборки исправленной программы и проверки поведения двух режимов; анализатор внутри него не запускается. Исходный вариант в `check.sh` не запускают до исправления.

Пустой отчёт после успешного анализа означает отсутствие находок выбранных проверок, а не доказанную безопасность всей программы. Сохранённые результаты разбора находятся в материалах лекции; преподавателю не требуется запускать инструменты во время занятия.

Проверено локально: Apple clang 16.0.0 на macOS arm64. Dockerfile подготовлен, но сборка контейнера не проверена: Docker daemon на машине подготовки не запущен.
